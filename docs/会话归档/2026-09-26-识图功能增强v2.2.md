## 关键决策

### 1. 技术选型：不引入 Python 聚合库，自己写 C# provider

调研发现最贴合的是 [kitUIN/PicImageSearch](https://github.com/kitUIN/PicImageSearch)（⭐726，Python，聚合 14 个引擎，MIT）与 [Decimation/SmartImage](https://github.com/Decimation/SmartImage)（⭐1346，**C#**，支持 SauceNao / IQDB / Ascii2D / trace.moe / Yandex / TinEye / ImgOps）。结论（转录 seq 84）：

> 因为你是 C#/.NET，务实做法是**照 SmartImage 的思路自己封装 HttpClient provider**（每个引擎一个类，统一返回 `{source, title, author, url, similarity}`），比引入 Python 混合打包干净得多。

理由是项目本体是自包含单文件 exe，不想为了识图再塞一个 Python sidecar。

### 2. 引擎优先级：SauceNAO 主力 → ascii2d 补漏，AnimeTrace 只作角色提示

转录 seq 147 给出的核实结论：

| 优先级 | 引擎 | 能提供什么 | 理由 |
| --- | --- | --- | --- |
| ★ 主力 | **SauceNAO** | `pixiv_id` / `member_id` / `member_name` / `title` / `similarity` | **唯一能直接吐 PID 的**，Pixiv 场景基本靠它 |
| ★ 补漏 | **ascii2d** | 来源页 URL（pixiv / twitter 都有），**不给 PID** | 覆盖 SauceNAO 未收录的图 |
| 兜底 | Yandex / Google Lens | 转载页、作者主页 | 无官方 API，只能抓，**明确不进核心链路**（稳定性差且可能违反 ToS） |
| 辅助 | AnimeTrace | 只能识别角色和出自哪部作品 | **给不了 PID**，对"重命名"只是提示；且实测 `api.animetrace.com/v1/search` 返回 **403** |
| 间接 | IQDB / 3D IQDB | Booru 站转载页 | 仅当 Pixiv 图被转到 booru 时有用 |

### 3. SauceNAO 的库索引优先（这是本次最有价值的决策之一）

不去猜索引号，而是**直接抓 `https://saucenao.com/index.php` 的搜索表单**（checkbox 的 `value` 就是 API 结果里的 `index_id` / db 位掩码），并参照官方 `https://saucenao.com/tools/examples/api/index_details.txt`。抓到并写进代码的映射（转录 seq 111、seq 117）：

| 位掩码 | index | 名称 |
| --- | --- | --- |
| `0x20` | #5 | **pixiv**（主库） |
| `0x40` | #6 | **pixivhistorical**（已删除/早期作品，**很多人漏掉这个**） |
| `0x10000000000` | #41 | Twitter |
| `0x400000000` | #35 | Pawoo |
| `0x80000000000` | #44 | Skeb |
| `0x800` / `0x100` | #11 / #8 | Nijie / Nico Nico Seiga |
| `0x200` `0x1000000` `0x2000000` `0x4000000` `0x1000` `0x8000000` | #9 / #25 / #26 / #27 / #12 / #28 | Danbooru / Gelbooru / Konachan / Sankaku / Yande.re / Anime-Pictures（转载站，最低优先） |

落进代码的排序（转录 seq 147 的骨架，现版本 `ReverseSearchService.cs` 的 `IndexRank`，数值越小越可信）：

```
5→0 pixiv | 6→1 pixivhistorical | 41→2 Twitter | 35→3 Pawoo | 44→4 Skeb | 11→5 Nijie | 8→6 Nico Seiga
9→7 Danbooru | 25→8 Gelbooru | 26→9 Konachan | 27→10 Sankaku | 12→11 Yande.re | 28→12 Anime-Pictures
```

**`pixivhistorical` 为什么重要**：它命中的作品在 pixiv 上通常已被删除，回查 pixiv API 会 404；此时应直接用 SauceNAO 返回的 `member_name` / `title` 兜底（或第三方代理 `pixiv.re/<pid>.jpg`）。

### 4. 双阈值 + dHash 像素级复核（专治误命名）

核心认知（转录 seq 147）：

> **SauceNAO 的 `similarity` 是匹配置信度，不是视觉相似度。** 在 50~75 区间，构图相似的图（同角色、同姿势）会被误判成同一张，对"自动重命名"是灾难。

因此定下三段式判定，并落到 `RenamerEngine.JudgeAsync`：

| 置信度 | 处理 |
| --- | --- |
| `≥ 85` | 直接采纳（高置信度） |
| `60 ~ 85` | **必须**下载来源缩略图做 dHash（64 位感知哈希）比对，汉明距离 ≤ 上限才采纳 |
| `< 60` | 丢弃 |

### 5. 感知分组：近似重复图只查一次

同一张图的不同分辨率 / 重存版本按 dHash 归为一组，一组只发一次识图请求，结果映射回全组。预期收益 30%~50% 的请求量（转录 seq 147 的吞吐设计，seq 438 的实际结论）。

### 6. pixiv 挂了也要继续识图

原实现里 pixiv 预检失败会 `return`，连识图一起跳过。用户机器上 pixiv 直连超时，等于识图功能完全不可用。改为只跳过 pixiv 元数据查询，识图照跑（新增开关 `ReverseWhenPixivDown`，默认 `true`）。

### 7. 用本地桩服务换取可验证性

真实约束是"SauceNAO 必须 API Key、ascii2d 被 Cloudflare 拦"，无法在真实网络上端到端验证。于是写了一个 Python（3 + Pillow）**本地 SauceNAO 桩服务**，按真实 API 的 JSON 结构返回，端到端验证解析 / 排序 / dHash 复核 / 感知分组。会话结束时把桩服务**留在项目里**成为离线回归工具 `scripts\mock-saucenao.py`（放 `%TEMP%` 会被清理，转录 seq 426）。

### 8. 其他工程决策

- dHash 用 **WPF 自身的图像管线**（`System.Windows.Media.Imaging`）实现，**不引入额外 NuGet 依赖**（转录 seq 222 的 `PerceptualHash.cs` 注释："复用 WPF 图像管线，不引入额外 NuGet 依赖。无法解码时返回 0"）。
- 上传用**文件字节**而不是 `url=` 参数：pximg 有防盗链，服务端抓不到。
- 上传前统一转 JPEG、长边压到 ~1200px（对匹配率几乎无损，上传更快）。
- 限频**不自己猜**：读响应 JSON 里 `header.short_limit` / `short_remaining`（短周期）与 `long_limit` / `long_remaining`（每日）自适应节流；`header.status != 0` 单独处理。
- 新增 `testmode=1`（dry-run，不消耗额度）与 `SauceNaoApiBase`（可指向自建中转/镜像），这样离线测试也能走真实代码路径。
- CLI 增加 `--limit N`（试跑）与 `--sauce-key KEY`。

### SauceNAO 请求参数（转录 seq 147 核实）

```
POST https://saucenao.com/search.php?output_type=2&db=999&numres=10&minsim=30&hide=0&api_key=...
Content-Type: multipart/form-data，字段名 file
```

- `dbmask=96`（`0x20|0x40`）= 只查 pixiv 两个库；不传 `dbmask` 用 `db=999` 查全库。
- `testmode=1` = dry-run，不消耗额度，专门用来联调。
- **一次请求拿全量候选**（`db=999 & numres=10 & minsim=30`），在客户端排序筛选，比"先查 pixiv 再查全库"省一半额度。
- 自适应节流示例（转录 seq 147 骨架）：`short_remaining <= 1` 等 30 秒，`<= 3` 等 5 秒。

### ascii2d 协议（核实自 PicImageSearch 源码）

- 按图上传：`POST https://ascii2d.net/search/file`，multipart 字段名 `file`。
- 按 URL：`POST /search/uri`，字段 `uri`。
- 返回 HTML 结果页，解析 `div.row > div.detail-box` 里的来源链接。
- 特征检索：`GET /search/bovw/<hash>`；颜色检索：`GET /search/color/<hash>`（默认）。

1. **真实命中率没能验证**（会话结尾原话）：当前环境 pixiv 直连超时、ascii2d 被 Cloudflare 挡、SauceNAO 匿名不可用。需要用户做两件事：
   - 在「pixiv / 识图」页填 SauceNAO API Key（<https://saucenao.com/user.php?page=account> 免费领取）
   - 挂代理（示例 `http://127.0.0.1:7890`）后点「测试网络」
2. 助手给出的建议试跑命令：
   ```bat
   PixivRenamer.exe --cli "D:\系统\下载\1\pixiv" --dry-run --limit 30
   ```
   然后看 CSV 的命中率与 `note` 列（复核差异值），确认无误再取消 `--dry-run`。
3. `dbmask=96`（只查 pixiv 两个库）虽然写进了 `SauceNaoDbMask`，但默认仍用 `db=999` 全库；两种策略的真实额度/命中率差异**未在会话中实测**。
4. AnimeTrace / IQDB 只做了调研，**没有接入**。
5. 会话里出现过两种缓存 key 说法：调研阶段写"**缓存 key 用 SHA-256 + dHash**"，同一节里也写过"SauceNAO … 缓存用图片 SHA-256 做 key（你已有查询缓存）"。最终实现的缓存 key 组合**未在会话中确认**。
6. 端到端验证全部基于**桩服务**，桩服务本身按"文件名 crc32%4"决定返回高分/中分/不匹配，属于人工构造的分布；它验证的是**链路正确性**，不是真实识别准确率。
